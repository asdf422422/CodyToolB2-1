# 테스트 및 최종 검수 기준

이 문서는 `docs/requirements.md`의 기능 인수 조건과 `docs/architecture.md`의 모듈·저장·스트리밍 규칙을 검증하는 방법을 정의한다. 기능 요구사항은 requirements에서, 구현 정책은 architecture와 `docs/decision.md`에서 관리한다. 같은 요구사항의 목록을 다른 문서에 복제하지 않는다.

## 테스트 원칙

- Python 표준 라이브러리의 `unittest`와 임시 디렉터리를 사용한다. 테스트는 사용자 데이터 디렉터리에 읽기·쓰기·삭제하지 않는다.
- 서비스 및 저장소 테스트는 임시 데이터 경로를 사용한다. CLI 테스트도 격리된 `--data-dir`을 지정한다.
- 테스트는 결과 코드와 함께 출력·저장 파일 상태를 확인한다. 실패를 무시하거나 테스트를 삭제해 통과시켜서는 안 된다.
- 정상 동작, 잘못된 사용자 입력, 저장 데이터 손상, 파일 접근 실패를 구분하여 검증한다.
- 오류가 발생한 경우 사용자 메시지와 종료 코드뿐 아니라 기존 데이터가 보존되는지도 확인한다.
- 확정 정책별 검증은 아래 기능 테스트를 따른다. 설계 결정이 바뀌면 해당 테스트와 requirements·architecture 문서를 함께 갱신한다.

## 필수 테스트 케이스

### 실행 환경과 모듈 구조

- 지원 기준 Python 3.10 이상에서 `python -m budget_app --help`가 실행된다.
- 표준 라이브러리만으로 실행되며, CLI 진입점이 종료 코드를 반환한다.
- CLI, 서비스, 저장소, 모델 책임이 분리되어 있고 요구사항에 정한 최소 모듈·클래스 수와 타입 힌트를 갖춘다.

### 모델, 입력 검증 및 거래 ID

- 유효한 거래의 필수 필드, 선택 메모·태그, CSV 왕복 결과를 확인한다.
- `type`은 `income`과 `expense`만 허용하고, 날짜는 실제 달력상 유효한 `YYYY-MM-DD`만 허용한다.
- 금액은 양의 정수만 허용한다. 0, 음수, 정수가 아닌 값 및 변환할 수 없는 입력을 거부한다.
- 필수 값 누락, 잘못된 월 형식, 잘못된 태그 입력 및 등록되지 않은 카테고리를 처리한다.
- 여러 거래를 만들었을 때 ID가 유일하고 기존 ID와 충돌하지 않는지 확인한다.
- 입력 실패가 저장 전 발생하면 거래 파일이 바뀌지 않는지 확인한다.

### 영구 저장소와 CSV 데이터 무결성

- 거래·카테고리·예산이 각각 별도 CSV 파일에 저장되고 UTF-8 및 헤더·필드 형식이 일관적인지 확인한다.
- 최초 사용 시 파일 생성 또는 안내가 요구사항 및 확정 정책과 일치하는지 확인한다. 기존 파일을 초기화하거나 덮어쓰지 않는지 확인한다.
- 파일이 없음, 비어 있음, 헤더만 있음, 필수 열 누락, 잘못된 행·자료형, 잘못된 인코딩, 읽기 권한 오류를 구분해 처리한다.
- 손상된 저장 레코드를 조용히 건너뛰거나 정상 데이터인 것처럼 보고하지 않는지 확인한다.
- 재실행 후에도 세 데이터 종류가 유지되고, 저장한 레코드와 다시 읽은 레코드가 일치하는지 확인한다.
- CSV quoting을 포함한 쉼표·따옴표·개행·한글이 메모 및 카테고리 값에서 안전하게 왕복되는지 확인한다.

### 거래 추가·목록·검색

- 대화형 `add`에서 유효 입력이 저장되고 성공 메시지와 생성된 ID가 표시된다.
- 잘못된 입력을 재입력받거나 사용자 오류로 종료할 때 내부 스택트레이스를 노출하지 않고 데이터를 변경하지 않는다.
- 빈 저장소의 `list`와 `search`는 오류 없이 빈 결과 안내를 표시한다.
- 목록·검색이 최신순이며 `--limit`과 기본 limit이 올바르게 적용된다.
- 검색의 `--from`, `--to`, `--category`, `--type`, `--q`, `--tag`를 각각 검증하고, 여러 조건을 조합했을 때 조건을 모두 만족하는 결과만 반환한다.
- 시작일이 종료일보다 늦은 경우, 잘못된 날짜·월·타입, 유효하지 않은 limit 등 잘못된 검색 조건을 거부한다.
- 날짜 오름차순 입력 데이터와 날짜가 같은 거래를 포함해 저장 순서가 최신순 조회 계약을 유지하는지 확인한다. 날짜가 같은 거래는 등록 순서대로 출력한다.

### 스트리밍과 최신순 저장

- 저장소 목록 및 검색 API가 제너레이터를 반환하고 파일을 한 레코드씩 순회하는지 확인한다.
- `list`와 `search`가 데이터를 모두 메모리에 적재한 뒤 정렬하지 않는지 코드 검토 및 대용량 데이터 테스트로 확인한다.
- 최신 날짜 우선 저장 불변 조건이 추가·수정·삭제 후에도 유지되는지 확인한다.
- 같은 날짜 거래의 등록 순서가 추가·수정·삭제 후에도 보존되는지 확인한다.
- 검색 필터가 제너레이터 순회 중 적용되고, limit에 필요한 결과까지만 소비하는지 확인한다.
- 파일이 비어 있거나 대량일 때도 메모리 사용을 위해 전체 파일을 무조건 리스트로 변환하지 않는다.

### 요약 및 예산

- 해당 월의 총수입, 총지출, 잔액(`수입 - 지출`)과 카테고리별 지출 합계를 검증한다.
- `--top N`이 지출 합계 내림차순으로 올바른 개수와 순서를 표시한다. 수입은 지출 합계에 포함하지 않는다.
- 거래가 없는 달의 안내 및 유효하지 않은 월·top 값 처리를 확인한다.
- 예산이 설정된 달의 예산액, 사용률(`월 총지출 / 예산 × 100`)과 초과 기준(지출이 예산을 초과함)을 확인한다.
- 예산 미설정 달에는 사용률이나 초과 경고를 임의 계산하지 않는다. 예산 금액은 양의 정수만 허용한다.
- 같은 월 예산 재설정은 기존 예산을 갱신하고 중복 월 레코드를 만들지 않는지 확인한다.

### 카테고리

- 추가·목록·삭제의 정상 동작과 각각의 성공·실패 메시지를 확인한다.
- 추가 시 카테고리 이름의 앞뒤 공백이 제거되고 대소문자만 다른 이름은 중복으로 처리되는지 확인한다.
- 빈 카테고리 파일에서 `FOOD`, `TRANSPORTATION`, `SHOPPING`, `HOUSING`, `ENTERTAINMENT`, `OTHERS`, `SALARY`, `SIDEINCOME`이 자동 생성되는지 확인한다.
- 사용 중인 카테고리 삭제가 차단되고 해당 카테고리 및 거래가 보존되는지 확인한다.
- 카테고리 변경 실패 시 거래 데이터와 카테고리 파일의 일관성이 유지되는지 확인한다.

### 거래 수정·삭제와 안전한 저장

- 존재하는 거래의 각 수정 가능 필드가 검증 후 반영되고, 수정 뒤에도 저장 순서 및 파일·목록 내용이 일치한다.
- 존재하지 않는 ID의 수정·삭제는 적절한 사용자 오류를 반환하고 파일을 변경하지 않는다.
- 옵션 기반 및 대화형 수정 경로가 모두 동작하고 동일한 필드 검증 및 저장 규칙을 따르는지 확인한다.
- 삭제 후 대상 거래만 제거되고 나머지 거래 및 ID는 유지된다.
- 임시 파일 쓰기, flush/교체 등 저장 과정에서 실패를 주입해 원본 파일이 온전하게 보존되는지 확인한다.
- 실패한 작업이 성공 메시지나 성공 종료 코드를 반환하지 않는지 확인한다.

### CSV 가져오기·내보내기

- 지정한 거래 CSV를 가져오고, 헤더·UTF-8·필수 및 선택 열·날짜·타입·등록 카테고리·양의 정수 금액·태그 변환을 검증한다.
- 잘못된 행만 건너뛰고 CSV 행 번호가 사용자에게 출력되는지 확인한다. 가져온 행과 건너뛴 행 수가 실제 처리 결과와 일치해야 한다.
- 날짜·금액·카테고리·타입·메모가 모두 기존 데이터와 일치하는 행 및 동일 가져오기에서 앞서 처리된 행과 일치하는 행은 건너뛰는지 확인한다. 태그만 다른 행은 중복으로 판정한다.
- 날짜·금액·카테고리·타입·메모 중 하나라도 다른 행은 중복으로 건너뛰지 않는지 확인한다.
- 중복 행에서 사용자 확인을 요청하지 않고, 가져오기 완료 후 중복 행이 있었음을 알리는지 확인한다.
- 입력 파일 부재, 읽기 권한 오류, 잘못된 CSV 문법, 필수 헤더 누락을 사용자 친화적으로 보고하고 스택트레이스를 노출하지 않는다.
- `export --out`은 월 또는 기간 조건을 요구하며, 경계 날짜 포함 여부와 결과 레코드가 필터에 맞는지 확인한다.
- 내보낸 CSV에 고정된 컬럼 순서와 헤더가 있고, UTF-8로 열어 재가져오기 가능한지 확인한다.
- 유효 행 반영 중 저장 실패를 주입했을 때 가져오기 전 거래 파일이 그대로 보존되고 성공 건수로 보고되지 않는지 확인한다.

### 데코레이터

- requirements에서 정한 데코레이터가 실제 함수에 적용되어 공통 관심사를 수행하는지 확인한다.
- 데코레이터 적용 전후 반환값이 동일하고 예외가 숨겨지거나 변환되지 않고 호출자에게 전달되는지 확인한다.
- 필요한 경우 `functools.wraps` 적용으로 함수 메타데이터가 보존되는지 확인한다.

### CLI와 오류 처리

- 각 최상위 명령과 하위 명령의 `--help`를 실행해 사용법을 표시하고 정상 종료하는지 확인한다.
- 정상 실행은 종료 코드 0, 잘못된 사용자 입력·업무 규칙 위반·파일 접근 실패는 0이 아닌 종료 코드를 반환한다.
- 잘못된 옵션, 필수 인자 누락, 잘못된 날짜·금액·월, 존재하지 않는 ID, 읽기·쓰기 실패에 대한 메시지를 확인한다.
- 사용자 오류 메시지에 traceback이나 내부 구현 세부사항이 포함되지 않는다.
- 오류 메시지가 실패 원인을 설명하고 수정 가능한 입력 오류에는 해결 힌트를 제공한다.
- 실패한 저장 작업이 성공으로 표시되지 않고, 예외가 여러 계층에서 중복 출력되지 않는다.

## 검증 명령

테스트 파일은 `tests/`에 애플리케이션 코드와 분리해 둔다. 표준 라이브러리 테스트 러너를 사용한다.

```sh
python -m unittest discover -s tests -v
python -m budget_app --help
```

각 명령·하위 명령의 help, 정상 경로 및 오류 종료 코드는 CLI 테스트에서 격리된 `--data-dir`을 사용해 검증한다. 전체 프로젝트의 필수 테스트 실행 후 README에 실제 사용 예시를 작성하면 예시 명령도 임시 디렉터리에서 재현한다. 아직 해당 테스트 모듈이나 CLI가 없다면 이를 완료한 것으로 간주하지 말고 미검증 항목으로 보고한다.

### 이번 검수에서 미실행

- Python 3.10 실행 검증은 해당 인터프리터가 환경에 없어 수행하지 않았다. Python 3.12에서 테스트와 CLI 실행을 확인했다.
- 대용량 파일을 사용한 목록·검색의 스트리밍 성능 및 메모리 검증은 요청에 따라 수행하지 않았다. 스트리밍 구현의 대규모 검증은 별도 검수가 필요하다.

## 완료 조건

프로젝트를 완료로 선언하려면 모두 충족해야 한다.

1. `docs/requirements.md`의 필수 기능과 입력 검증을 구현하고 직접 관련 테스트로 확인한다.
2. 거래·카테고리·예산이 각각 CSV에 영구 저장되며 재실행 후 유지된다.
3. 목록·검색의 제너레이터 스트리밍, 최신순 저장 순서 및 limit 동작을 확인한다.
4. 수정·삭제 및 가져오기 실패 상황에서 데이터 손상 여부를 검증하고 원본 보존 계약을 만족한다.
5. 데이터 ID 유일성, 카테고리·예산 규칙, 요약 계산 및 CSV 교환 동작을 확인한다.
6. 데코레이터의 실제 적용, 반환값·예외 전파와 CLI help·오류 메시지·종료 코드를 검증한다.
7. `docs/decision.md`에서 필수 기능과 관련된 정책이 확정되어 있고 구현·테스트·README가 해당 결정과 일치한다.
8. README의 실행 예시를 재현하고, README 및 필수 문서가 실제 구현과 일치한다.
9. `python -m unittest discover -s tests -v`를 포함한 필수 검증이 통과한다. 실행하지 못한 테스트나 환경 제약은 완료 보고에 명시한다.
