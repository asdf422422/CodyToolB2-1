Architecture Guide
1. 목적 및 기본 원칙

이 문서는 용돈 기입장 프로젝트의 아키텍처, 모듈별 책임, 데이터 모델, 파일 저장 정책 및 모듈 간 인터페이스를 정의한다.

모든 구현은 AGENTS.md와 docs/requirements.md를 준수해야 한다.

설계 원칙:

단순하고 유지보수하기 쉬운 구조를 우선한다.
각 모듈은 명확한 단일 책임을 갖는다.
비즈니스 로직과 CLI 입출력 및 파일 I/O를 분리한다.
데이터 검증과 오류 처리는 일관된 규칙을 따른다.
데이터 손실과 불완전한 파일 쓰기를 방지한다.
외부 라이브러리 없이 Python 표준 라이브러리만 사용한다.
요구사항에 필요하지 않은 추상화와 복잡성을 추가하지 않는다.
2. 기술 기준
Python 3.10 이상
CLI 실행: python -m budget_app <command> [options]
내부 저장 형식: CSV
외부 거래 가져오기 및 내보내기: CSV
데이터 저장 디렉터리 기본값: ./data
저장 디렉터리 변경 옵션: --data-dir
의존성: Python 표준 라이브러리만 사용

내부 저장 형식과 외부 거래 교환 형식은 모두 CSV이며, 각 데이터 파일은 별도 파일로 유지한다.

최소 3개 이상의 Python 모듈로 분리한다.
거래, 카테고리, 예산을 각각 별도 파일에 저장한다.
CLI, 모델, 저장소, 서비스의 책임을 구분한다.
테스트 파일을 애플리케이션 코드와 분리한다.
요구사항 충족에 불필요한 모듈을 추가하지 않는다.
4. 모듈별 책임
__main__.py

책임:

python -m budget_app 실행 진입점 제공
CLI 실행 함수 호출
최종 종료 코드 반환

규칙:

비즈니스 로직을 직접 구현하지 않는다.
파일 저장 및 데이터 검증 로직을 직접 구현하지 않는다.
cli.py

책임:

argparse를 이용한 명령어 및 옵션 정의
--help 지원
대화형 입력 처리
사용자에게 결과 및 오류 메시지 출력
서비스 계층 호출
오류를 적절한 종료 코드로 변환

규칙:

거래 합계나 예산 사용률을 직접 계산하지 않는다.
파일을 직접 읽고 쓰지 않는다.
명령어의 입력 및 출력 계약을 유지한다.
models.py

책임:

데이터 모델 정의
모델의 필드와 타입 명시
모델 수준의 기본적인 불변 조건 정의

기본 모델:

Transaction
Category
Budget

거래 모델은 dataclass 사용을 권장한다.

from dataclasses import dataclass


@dataclass
class Transaction:
    id: str
    type: str
    date: str
    amount: int
    category: str
    memo: str = ""
    tags: list[str] | None = None


위 코드는 필드 구성을 설명하기 위한 예시다. 실제 구현에서는 type의 허용값, 날짜 형식, 양수 금액, 태그의 기본값 및 유효성 검증을 함께 정의한다.

가능하면 태그는 기본값을 빈 리스트로 설정하고, 인스턴스 간에 가변 객체를 공유하지 않도록 한다.

repositories.py

책임:

영구 저장 파일의 생성 및 접근
데이터 읽기와 쓰기
CSV 직렬화 및 역직렬화
제너레이터 기반 스트리밍
거래 수정 및 삭제 시 안전한 파일 갱신
저장 데이터의 구조 검증 및 저장소 오류 처리

필요한 저장소:

TransactionRepository
CategoryRepository
BudgetRepository

규칙:

CLI가 파일 경로나 직렬화 형식을 직접 다루지 않도록 한다.
파일을 읽는 공통 경로에서 인코딩과 형식을 일관되게 처리한다.
수정 및 삭제는 임시 파일 작성 후 교체하는 방식을 우선 고려한다.
저장 실패를 성공으로 처리하지 않는다.
저장소는 비즈니스 정책을 불필요하게 중복 구현하지 않는다.
services.py

책임:

거래 추가, 검색, 수정, 삭제
월별 요약 계산
예산 설정 및 사용률 계산
카테고리 관리 및 사용 중인 카테고리 삭제 방지
CSV 가져오기·내보내기 작업 조정
저장소와 모델을 이용한 비즈니스 규칙 적용

서비스는 CLI에 종속되지 않아야 하며, 터미널 입출력 대신 반환값 또는 명확한 예외를 사용한다.

필요한 경우 기능별 서비스 클래스로 분리할 수 있지만, 단순한 기능을 위해 과도하게 클래스를 늘리지 않는다.

validators.py

책임:

날짜 및 월 형식 검증
거래 타입 검증
양수 금액 검증
카테고리 이름 검증
검색 기간 및 옵션 검증
CSV 입력 필드 검증

검증 함수는 명확한 입력 및 출력 타입을 가지도록 한다.

동일한 검증 규칙을 CLI와 서비스에서 서로 다르게 구현하지 않는다. 입력 단계에서 사용자에게 재입력을 요청할 수 있지만, 서비스 계층에서도 비즈니스 규칙 위반을 방지해야 한다.

utils.py

책임:

공통 데코레이터
실행 로그 또는 실행 시간 측정
공통적으로 필요한 보조 기능

규칙:

범용 유틸리티만 둔다.
특정 도메인 기능이나 핵심 비즈니스 로직을 무분별하게 모으지 않는다.
데코레이터 구현을 둘 수 있으며, 적용 대상과 공통 관심사 선택은 docs/requirements.md를 따른다.
데코레이터는 반환값과 예외 전파를 보존하고, 필요한 경우 functools.wraps로 메타데이터를 보존한다.
5. 모듈 간 의존 관계

기본 의존 방향은 다음과 같다.

__main__.py
    |
    v
  cli.py
    |
    v
services.py
    |
    +----------> repositories.py
    |                  |
    v                  v
validators.py       data files
    |
    v
models.py


utils.py는 필요한 모듈에서만 사용한다.

의존성 원칙:

모델은 CLI나 저장소 구현에 의존하지 않는다.
저장소는 CLI에 의존하지 않는다.
서비스는 CLI의 출력 형식이나 input() 호출에 의존하지 않는다.
CLI는 비즈니스 규칙을 중복 구현하지 않는다.
모듈 간 순환 import를 만들지 않는다.

위 그림은 개념적인 의존 관계다. 실제 구현에서는 models.py를 CLI, 서비스, 저장소가 공통으로 참조할 수 있으며, 검증 함수도 필요한 계층에서 사용한다.

6. 데이터 모델
Transaction

필수 필드:

필드	타입	규칙
id	str	유일해야 함
type	str	income 또는 expense
date	str	YYYY-MM-DD
amount	int	양의 정수
category	str	등록된 카테고리
memo	str	선택 항목
tags	list[str]	선택 항목

금액은 정수로 관리한다. 금액 계산 시 불필요한 부동소수점 오차가 발생하지 않도록 한다.

Category

기본 필드:

name: 카테고리 이름

카테고리 이름은 앞뒤 공백을 제거해 저장하고, 비교 및 중복 판정 시 대소문자를 구분하지 않는다.

Budget

기본 필드:

month: YYYY-MM
amount: 양의 정수

월별 예산은 월을 기준으로 조회 및 관리한다. 같은 월 예산 재설정 정책은 docs/decision.md에서 관리한다.

7. 영구 저장 정책
저장 파일
데이터	파일 예시	내용
거래	transactions.csv	거래 레코드
카테고리	categories.csv	카테고리 레코드
예산	budgets.csv	월별 예산 레코드

각 파일은 서로 독립적으로 영구 저장한다.

공통 규칙
기본 디렉터리는 ./data다.
--data-dir로 저장 위치를 변경할 수 있어야 한다.
세 저장 파일이 없으면 생성한다. 카테고리 파일이 비어 있으면 `FOOD`, `TRANSPORTATION`, `SHOPPING`, `HOUSING`, `ENTERTAINMENT`, `OTHERS`, `SALARY`, `SIDEINCOME`을 자동 등록한다. 기존 데이터 파일은 초기화 과정에서 덮어쓰지 않는다.
CSV 파일은 헤더를 포함하며 각 레코드는 한 행으로 저장한다.
파일 인코딩은 UTF-8로 통일한다.
내부 CSV의 거래 컬럼은 `id,type,date,amount,category,memo,tags`, 카테고리 컬럼은 `name`, 예산 컬럼은 `month,amount` 순서로 고정한다. 내부 거래 CSV의 `tags` 값은 JSON 문자열 배열로 직렬화한다.
필수 필드가 없거나 자료형이 잘못된 레코드는 조용히 무시하지 않는다.
데이터 오류는 원인을 확인할 수 있도록 보고한다.
기존 데이터가 있는 경우 초기화 과정에서 이를 임의로 덮어쓰지 않는다.
ID 생성

거래 ID는 중복되지 않아야 한다.

ID 생성 방식은 한 곳에서 관리하며, 기존 ID와의 충돌을 방지한다. 파일 기반 프로그램에서는 여러 프로세스가 동시에 쓰는 상황을 별도로 지원하지 않는 한 단일 프로세스 사용을 기본 전제로 한다.

8. 스트리밍 및 정렬 정책

거래 목록과 검색은 제너레이터 기반으로 파일을 순차적으로 읽는다.

yield를 사용해 거래 레코드를 순차적으로 전달한다.
검색 조건은 가능한 한 레코드를 읽는 과정에서 적용한다.
전체 파일을 무조건 메모리에 적재하지 않는다.
--limit은 필요한 결과만 출력하도록 활용한다.
목록 및 검색 결과의 기본 limit은 20건이다.

저장 순서는 날짜 내림차순으로 유지한다. 날짜가 같은 거래는 등록 순서를 유지한다. 추가·수정 시에도 이 정렬 불변 조건을 보장한다. 저장소는 한 행씩 읽어 제너레이터로 전달하고, 검색 필터는 순회 중 적용한다. 따라서 목록과 검색은 전체 파일을 메모리에 적재하거나 다시 정렬하지 않고 최신순을 유지한다.

9. 수정 및 삭제의 데이터 안전성

거래 수정과 삭제는 파일을 직접 부분 수정하는 대신 다음 절차를 우선 고려한다.

기존 데이터를 순차적으로 읽는다.
변경 사항을 임시 파일에 기록한다.
쓰기 작업이 성공했는지 확인한다.
임시 파일을 원본 파일과 같은 파일 시스템에 두고 원자적 교체를 수행한다.
실패 시 기존 파일을 보존하고 임시 파일 정리 여부를 검토한다.

원자적 교체는 일반적인 파일 교체 과정의 위험을 줄이지만, 모든 종류의 시스템 장애에 대한 완전한 내구성을 자동으로 보장하지는 않는다.

동일 파일에 대한 동시 쓰기 지원은 기본 범위에 포함하지 않는다. 필요해질 경우 별도의 잠금 및 동시성 정책을 설계한다.

10. CSV 가져오기 및 내보내기

가져오기·내보내기 CSV는 다음 스키마를 사용한다.

컬럼	필수	형식
date	예	YYYY-MM-DD
type	예	income 또는 expense
category	예	등록된 카테고리
amount	예	양의 정수
memo	아니요	문자열
tags	아니요	쉼표 구분 문자열

규칙:

UTF-8 및 헤더를 사용한다.
표준 라이브러리의 csv 모듈을 사용한다.
CSV를 단순 문자열 분리 방식으로 파싱하지 않는다.
가져온 데이터는 저장 전에 유효성을 검증한다.
잘못된 행은 건너뛰고 CSV 행 번호를 사용자에게 보고한다.
기존 거래 또는 이번 가져오기에서 앞서 처리한 행과 날짜·금액·카테고리·타입·메모가 모두 일치하는 행은 중복으로 건너뛴다. 태그는 중복 판정에 포함하지 않는다. 사용자 확인을 요청하지 않고 가져오기 완료 후 중복 행이 있었음을 알린다.
유효한 행은 가져오기 입력을 모두 읽고 검증한 뒤 한 번의 원자적 저장으로 반영한다. 저장에 실패하면 가져오기 전에 있던 거래 파일을 보존한다.
가져오기 및 내보내기 처리 건수를 보고한다.
내보내기 결과는 지정한 월 또는 기간 조건을 만족해야 한다.
CSV의 tags 문자열은 내부의 태그 목록으로 변환한다.
11. 예산 및 카테고리의 일관성
예산
월별 예산은 해당 월의 지출과 비교한다.
사용률은 부동소수점 오차를 피하도록 정수 금액을 Decimal로 변환해 해당 월 총지출 / 월 예산 × 100으로 계산한다.
예산 초과 여부는 지출이 예산을 초과했는지 기준으로 판단한다.
예산이 설정되지 않은 경우 사용률이나 초과 여부를 임의로 계산하지 않는다.
예산이 0인 상태는 허용하지 않는다.
카테고리 지출 합계는 내림차순으로 표시하며 합계가 같으면 카테고리 이름의 대소문자 무시 오름차순으로 정렬한다.
카테고리
거래를 추가하거나 수정할 때 카테고리 등록 여부를 검증한다.
사용 중인 카테고리는 삭제를 차단하거나 대체 카테고리를 요구한다.
카테고리 변경 후 기존 거래가 유효하지 않은 상태로 남지 않도록 한다.
기본 카테고리, 카테고리 중복·삭제, 예산 재설정 정책은 docs/decision.md에서 관리한다.
12. 오류 처리 및 데코레이터
사용자 입력 오류는 재입력 또는 이해하기 쉬운 오류 메시지로 처리한다.
저장소 오류는 서비스와 CLI가 적절하게 전달받아 처리한다.
CLI에서 최종 오류 메시지와 종료 코드를 결정한다.
스택트레이스를 일반 사용자에게 노출하지 않는다.
예상 가능한 예외만 명시적으로 처리하며, 모든 예외를 무조건 무시하지 않는다.

오류 처리 정책은 이 절의 CLI 및 저장소 규칙을 따른다. 데코레이터 요구사항과 충족 조건은 docs/requirements.md에서 관리한다.

13. CLI 인터페이스

CLI는 argparse를 사용해 구현한다.

모든 명령은 --help를 제공한다.
옵션 표기는 -- 형식으로 통일한다.
add는 대화형 입력을 기본으로 한다.
update는 옵션 기반과 대화형 입력을 모두 지원한다. 각 방식의 사용 예시를 README에 명시한다.
delete는 --id를 사용한다.
budget set은 --month 및 --amount를 사용한다.
import는 --from, export는 --out을 사용한다.
export는 월 또는 기간 조건을 필수로 받는다.
저장 디렉터리는 --data-dir로 변경할 수 있다.

명령어의 상세 인자와 동작은 docs/requirements.md를 기준으로 한다.

14. 테스트 및 유지보수

테스트는 실제 사용자 데이터에 영향을 주지 않도록 임시 디렉터리를 사용한다.

테스트 케이스와 완료 기준은 docs/testing.md에서 관리한다. 정책과 설계 결정의 근거는 docs/decision.md에서 관리한다.

아키텍처를 변경할 때는 다음을 확인한다.

변경 이유가 명확한가?
필수 요구사항을 유지하는가?
기존 모듈의 책임을 불필요하게 넓히지 않는가?
테스트와 문서를 함께 갱신했는가?
더 단순한 구현으로 같은 목적을 달성할 수 없는가?
15. 아키텍처 변경 원칙

AI Agent는 이 문서의 구조를 무조건 기계적으로 따르기보다, 명시된 책임과 필수 제약을 유지해야 한다.

단, 다음 변경은 사용자 확인 없이 임의로 수행하지 않는다.

내부 저장 포맷 변경
데이터 파일 구조 변경
필수 기능 제거 또는 동작 변경
데이터 삭제나 초기화 정책 변경
외부 라이브러리 도입
요구사항과 충돌하는 아키텍처 변경

작업을 완료하면 변경된 파일, 검증 결과, 미완료 항목 및 아키텍처와 다른 부분이 있다면 그 이유를 보고한다.
